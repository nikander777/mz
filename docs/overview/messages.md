# Сообщения

> Личная переписка между пользователями маркетплейса — покупатель ↔ продавец, диалоги один-на-один. Работает в реальном времени (WebSocket/Reverb). Полный технический разбор — в приложении [Техническая справка](/processes/).

## Назначение и роли

Раздел «Сообщения» — это личные диалоги между пользователями: вопросы по товару, обсуждение сделки, уточнения перед покупкой. Основной сценарий — переписка **покупатель ↔ продавец** один-на-один (private-диалог).

| Актор | Что делает |
|---|---|
| Покупатель | Пишет продавцу с карточки товара, из профиля продавца, из карточки заказа или напрямую из раздела «Сообщения» |
| Продавец | Отвечает на вопросы, ведёт диалог по сделке |
| Участник диалога (роль) | В групповых диалогах роль хранится как `owner` (создатель) или `member`; в личных диалогах роль в логике не используется |

::: warning Внимание — отдельная подсистема «Чат по заказу»
Внутри карточки заказа есть **отдельный** чат (endpoint `POST /api/orders/{order}/messages`, компонент `OrderChat`). Это НЕ те же диалоги, что в разделе «Сообщения»: другая таблица данных, другой контроллер, без реалтайма через Reverb. Не путать эти две системы при тестировании.
:::

Интерфейс раздела «Сообщения» построен целиком под личные диалоги — везде показывается имя/аватар собеседника.

## Как открывается диалог

Точки входа, ведущие на `/messages?seller=<id>&product=<id>`:

- **Карточка товара** — «Написать продавцу» (передаёт `seller` и `product`).
- **Профиль продавца** — «Написать» (передаёт только `seller`, без товара).
- **Кнопка покупки** на карточке — с защитой: если товар ваш собственный, показывается тост «Вы не можете написать сами себе» и переход не выполняется.
- **Карточка заказа** — переход к диалогу с продавцом/покупателем.
- **Сам раздел «Сообщения»** — выбор существующего диалога из списка.

### Пошаговый флоу открытия диалога с продавцом

При заходе на `/messages` с параметрами `?seller=&product=` система выполняет:

1. Читает `seller` и `product` из адреса.
2. Ищет **уже существующий** личный диалог с этим продавцом в загруженном списке.
   - **Ветка A — диалог найден:** открывает его. Если передан `product` — отправляет автоприветствие с товаром.
   - **Ветка B — диалог не найден:** создаёт новый личный диалог (`POST /conversations`). На бэкенде срабатывает идемпотентный `findOrCreatePrivate` — если пара пользователей уже имеет диалог, дубль не создаётся. Затем диалог открывается, при наличии `product` шлётся автоприветствие.
   - **Ветка ошибки:** тост «Не удалось открыть диалог с продавцом».
3. **Автоприветствие по товару:** система подтягивает товар (`GET /api/public/products/{id}`) и отправляет сообщение вида «Здравствуйте! Меня интересует ваш товар: {исполнитель} — {название}». Если товар не загрузился — ошибка тихо логируется, приветствие не отправляется (диалог всё равно открыт).

## Отправка сообщения — по шагам

При нажатии «Отправить» (`POST /api/conversations/{id}/messages`) сервер последовательно проверяет:

1. Пользователь авторизован — иначе **401**.
2. Диалог существует — иначе **404**; пользователь является участником — иначе **403**.
3. Валидация: `content` до 5000 символов (может быть пустым), `type` из `text|image|file`, `attachment_ids` — массив до 10 элементов, каждый существует.
4. **Гейт «пусто»:** если нет ни текста, ни вложений — **422** «Сообщение должно содержать текст или вложение».
5. **Проверка вложений:** каждое вложение должно принадлежать отправителю И быть ещё не привязанным (orphan). Иначе — **422** «Некоторые вложения недоступны». Это защита от привязки чужого или уже отправленного файла.
6. В транзакции: создаётся сообщение (проставляется `delivered_at`), к нему привязываются вложения, событие `MessageSent` рассылается остальным участникам. Рассылка обёрнута в отдельный `try/catch` — если Reverb недоступен, сообщение всё равно сохранится (ошибка вещания только логируется). Ответ **201** с телом сообщения.
7. Ошибка внутри транзакции → откат → **500** «Failed to send message».

## Прочтение сообщений

- **Открытие диалога** (`GET /conversations/{id}` или `POST /conversations/{id}/read`) — счётчик непрочитанных обнуляется автоматически.
- **Отметка одного сообщения прочитанным** — срабатывает только для **чужого** сообщения; проставляется `read_at`, автору сообщения летит событие `MessageRead` (его галочка становится «двойной»). Повторная отметка идемпотентна.
- **Массовая отметка «прочитать всё»** — все чужие непрочитанные получают `read_at`, счётчик обнуляется. **Но событие `MessageRead` при этом НЕ рассылается** — у собеседника галочки «прочитано» массово не обновятся в реалтайме, только после перезагрузки страницы.

## Индикатор «печатает…»

При наборе текста клиент шлёт `POST /conversations/{id}/typing`, событие `UserTyping` рассылается остальным участникам. Собеседник видит «печатает…» только если находится в этом же активном диалоге.

## Вложения

1. Пользователь выбирает файл — он сразу загружается (`POST /api/messages/attachments`, отдельным запросом до отправки сообщения).
2. Ограничения на бэкенде: **максимум 100 МБ**, разрешены только **изображения** (jpeg, png, webp, gif, heic, heif) и **видео** (mp4, quicktime, webm, m4v, matroska). Прочие типы — **422** с русским сообщением.
3. Файл кладётся в хранилище `s3-media` по пути `chat/{userId}/{ULID}.ext`, создаётся «orphan»-вложение (ещё не привязанное к сообщению).
4. При отправке сообщения id вложений передаются и привязываются.
5. **Удаление до отправки** (`DELETE /messages/attachments/{id}`): **403** если не владелец, **422** если вложение уже привязано к отправленному сообщению, иначе файл и запись удаляются.

## Закрепление сообщения (pin)

`POST /conversations/{id}/pin` с `message_id`: **403** если не участник, **422** если сообщение не из этого диалога. Иначе сообщение закрепляется, участникам рассылается `ConversationPinChanged`, интерфейс обновляет и список, и активный диалог. `DELETE` снимает закрепление.

## Уведомления о новых сообщениях

По событию `MessageSent` слушатель `SendNewMessageNotification` шлёт уведомление каждому активному участнику, кроме автора. Каналы зависят от настроек пользователя (категория «Сообщения»):

| Канал | Условие отправки |
|---|---|
| Email | Если включён email-канал, есть подтверждённый email, **и** прошло ≥ 5 минут с последнего письма по этому диалогу-получателю |
| Telegram | Если привязан `telegram_chat_id` |
| Max | Если привязан `max_user_id` |

На сайте уведомления: тип `new_message`, id диалога и сообщения, отправитель, текст обрезается до 120 символов. Email использует отдельный шаблон.

## Онлайн-статус

Статус «Онлайн» = пользователь был активен в пределах последних 5 минут (`last_active_at`). Активность обновляется middleware при аутентифицированных запросах, но намеренно **не на всех** маршрутах (ради экономии записи в БД) — поэтому статус может слегка «отставать».

## Интерфейс

Двухколоночный экран: слева — список диалогов (со счётчиком непрочитанных), справа — активный чат. В шапке чата: собеседник, статус **«Онлайн»**, закрепление и меню.

## Все сценарии и крайние случаи

| Ситуация | Что происходит |
|---|---|
| Пустое сообщение (без текста и вложений) | **422**, не отправляется |
| Текст длиннее 5000 символов | **422** валидация |
| Более 10 вложений | **422** (лимит 10) |
| Чужое или уже отправленное вложение | **422** «недоступны» |
| Файл > 100 МБ или неподдерживаемый тип | **422** |
| Не участник диалога | **403** на любом действии |
| Несуществующий диалог/сообщение | **404** |
| Неавторизован | **401** |
| Повторное создание диалога с тем же продавцом | Дубль не создаётся |
| Собеседник вышел из диалога (`left_at`) | Имя/аватар берутся из самого диалога (fallback), сообщения ему не рассылаются; сам вышедший теряет доступ к истории (403) |
| Автор сообщения удалён | Явной обработки нет; интерфейс показывает заглушку «U» вместо аватара, не падает |

## Техническая часть

Каналы реального времени (Reverb/WebSocket, приватные каналы, кастомная авторизация вещания), модель данных диалогов и вложений, слушатель уведомлений и точки интеграции — приложение [Техническая справка](/processes/).
